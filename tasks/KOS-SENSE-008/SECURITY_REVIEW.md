## 1. Scope, method and limits

Scope: the threat model entry points EP-1 to EP-16 of the repository as it is. Method: reading the code and the workflows; probing the command lines with crafted inputs (malformed, empty, binary, very large, deeply nested, wide, huge integers, NaN, invalid UTF-8, missing files, directories, symbolic links); loading controlled temporary consumer modules in separate interpreters; an automated policy check of every workflow; inspection of the build configuration and of the contents of the release artifacts; running every test suite with the network disabled. Each statement that can be tested is covered by a test in `tests/security/`; the test name is given in the register or in the section.

Limits: an internal review of a small standard-library-only code base by its own team. No external scanner, fuzzer or dependency auditor was part of acceptance (the runtime has no dependency to audit). No test of the GitHub-hosted settings that are not in the repository (branch protection, rulesets, private vulnerability reporting, secrets stored in the settings): they are stated as unverified. Only Linux and Python 3.12 were exercised.

## 4. Review by area

### Input handling (AC-802)

Entry points EP-1 to EP-4. Malformed, oversized, deeply nested, wide input and path misuse were probed. One defect class (F-001, deep nesting) and one resource bound (F-003) were found and fixed; the rest are confirmed non-issues (N-1 to N-5). The decoder's recursion limit is a property of the Python standard library: JSON nested beyond about a thousand levels is rejected as unreadable (exit 2). Documents larger than memory are not specially handled: the commands read a file completely, as their documentation says.

### Consumer loading (AC-803)

Entry point EP-5. The cases tested with controlled temporary modules written by the tests, each in a separate interpreter: a valid consumer object, class and factory; a module that raises, calls `sys.exit()` or contains a syntax error at import; a missing attribute; an attribute that is not callable or is `None`; a consumer missing an operation; a factory that raises or exits; a consumer that raises or exits when invoked; a hostile decision object; two consumers of which one fails; a consumer and a module that hang (the child is ended by a subprocess timeout that belongs to the test); invalid specifications. **Loading is not a sandbox.** The imported module runs in the harness process with the privileges of the user; a timeout, where an operator adds one, ends the process and does not isolate or make the consumer safe. The documentation (`src/kritva_sense/CONFORMANCE.md`) and this report say so. No untrusted code was run.

### Workflows and the PR gate (AC-804)

Reviewed one by one against the merged state after pull requests #50 and #51. The automated policy is `tests/security/test_workflows.py`. It is a constrained pattern check over the workflow text, not a YAML parser: it can miss anchors and aliases, job-level permission overrides, reusable workflows or composite actions, so it does not prove the effective token permissions. After any workflow change a person reads the effective YAML; the test only stops the known patterns from returning, and a new or changed workflow fails it until it is reviewed and the policy is updated.

Offline requirement. Three layers, strongest first. (1) `RealNetworkNamespace` in `tests/security/test_offline.py` runs every mandatory suite (contract, frame graph, generator, stream, conformance, status, security and packaging) inside a real Linux network namespace with no interface and no route; a probe first proves that a connection attempt fails with `ENETUNREACH`. The packaging suite uses a pre-created wheelhouse of the hash-pinned build tools (`KRITVA_WHEELHOUSE`) and every mandatory packaging test executes (`PACKAGING-EVIDENCE mandatory=N executed=N`). The test prints a `NETNS-EVIDENCE` line with the test count of each suite. It tries an unprivileged user namespace (`unshare -rn`), then passwordless `sudo` with `unshare -n` and `setpriv` (GitHub-hosted runners), then root; in CI a machine that can create none of them fails the test, on a developer machine it is a skip with the reason. (2) Python-level diagnostics: the same suites with socket connection and name resolution blocked by a `sitecustomize` module, and the packaging suite with the package index pointed at a dead address, because that suite removes `PYTHON*` variables on purpose. These are diagnostics only and are not, alone, the proof (a test could start Python with `-I` or run a non-Python tool). (3) Source inspection: `NetworkTestsAreIdentified` greps the test sources for network calls; it is a substring check and can miss aliases and helpers, so it supports the first two layers and replaces neither. The one test that needs the network is `test_every_mandatory_suite_passes_in_a_network_namespace` (with its sibling `test_packaging_suite_passes_offline_with_a_prepared_wheelhouse`): each prepares the wheelhouse online (the only fetch of the repository tests, of the hash-pinned build tools) before the suites run without the network; they are excluded from the offline suite (`KRITVA_OFFLINE_SUITE=1`) and justified in the module. A missing mandatory build tool fails CI whichever indicator (`CI` or `GITHUB_ACTIONS`) marks the run (`test_in_ci_a_missing_build_tool_fails_the_run`, `test_in_ci_detected_only_by_github_actions_a_missing_build_tool_still_fails`, `test_in_ci_an_unusable_wheelhouse_fails_the_run`), and a security check that cannot run fails CI instead of skipping (`secutil.unavailable`). Review evidence taken in the cloud review environment (not part of acceptance): every suite also passed inside `unshare -rn` with the wheelhouse: contract 27, frame graph 36, generator 48, stream 67, conformance 53, status 5, packaging 27 and security 86 tests.

## 6. Final report

Conclusion. The repository's commands, consumer loading, workflows and build path were reviewed against the threat model. Three defects (two Medium, one Low) and one documentation gap were fixed with regression tests; four further findings were fixed in owner-merged protected-path pull requests (F-004 in the repository only); three Low findings are accepted by the risk owner with their residual risk. Not verified by this review: that the GitHub ruleset requires the `unit-tests` check, and the other settings outside the repository files. Each statement in sections 3 and 4 is backed by a test or by the named review step.

Explicit non-claims. This review is **not a certification**, a penetration test or an audit by an independent party. The consumer loader is **not a sandbox**, and a timeout does not make it one. The review makes **no safety claim**: nothing here concerns hardware, a sensor, a robot or operational safety, and it does not show that the repository is free of vulnerabilities; it records what was examined, what was found and what was done. The review is the interim D-047 role and is not independent for the task itself. It does not verify the settings that live outside the repository files. The test data are synthetic.

Evidence. `make test-unit` and `tests/security/` pass in CI on the closing commit and in a network-disabled run; closing commit a8dfb5a7827e9888a5bfae0bbcea1598727bd400, `unit-tests` run 41298259048 PASS (make check, docs-check and test-unit, including the security suite and the real network-namespace run), retest evidence and merge commit for each fixed finding in the register.
